# Guitar Vault

Application Java 21 / Spring Boot pour gérer une collection privée d’instruments, les documents et rapports de luthiers, les transferts de propriété, les groupes et les demandes de studio.

## Guides utilisateurs et aide intégrée

- [Guides utilisateurs en français et anglais](docs/user-guide/README.md) : premiers pas, collection, documents et archives, luthiers, transferts, groupes et studios, questions fréquentes.
- Dans l’application : **Aide et guides** dans la navigation, ou `/help` (accessible sans connexion).
- Les pages d’aide utilisent les mêmes fichiers `.md` que Git. Le menu de langue sélectionne la version française ou anglaise ; les liens entre guides restent dans la langue choisie. Chaque guide propose le téléchargement de son source Markdown.

Pour modifier l’aide, éditer `docs/user-guide/fr/*.md` et `docs/user-guide/en/*.md`, puis reconstruire et redémarrer l’application. Maven inclut ces fichiers dans le JAR, sous `help/` : aucun accès au dépôt ni chemin local n’est nécessaire à l’exécution. Le catalogue explicite de `HelpService` limite les pages publiées aux guides enregistrés ; les autres fichiers du dépôt ne sont pas exposés. Les liens relatifs entre guides sont adaptés aux routes `/help/{slug}` à l’affichage. Le rendu [CommonMark](https://github.com/commonmark/commonmark-java) échappe le HTML brut et filtre les URL dangereuses.

Voir [les consignes de maintenance des guides](docs/user-guide/README.md#maintaining-the-guides). Les tests `HelpTests` vérifient le contenu source, les deux langues, les liens, les téléchargements, les fichiers non exposés et la sécurité du rendu. Le parcours Chromium contrôle aussi l’accès sans compte, la navigation et la mise en page mobile.

## Test bêta avec trois participants

Le [kit de test bêta](docs/beta/README.md) prépare une session propriétaire / acheteur / luthier : missions en français et anglais, fichiers fictifs, vérifications de confidentialité et modèle de notes. Il utilise l’instance de démonstration locale et des profils navigateur distincts, sans réinitialiser les données existantes. Les [résultats automatisés](docs/beta/automated-results.md) sont séparés des observations humaines, qui restent à recueillir. Ces documents de test ne font pas partie du catalogue public `/help`.

## Fixtures de démonstration

Depuis le dossier `guitar-vault`, lancer :

```sh
./mvnw spring-boot:run -Dspring-boot.run.profiles=fixtures
```

Ouvrir <http://localhost:8082>. Le profil `fixtures` utilise la base persistante distincte `data/guitarvault-demo.mv.db` et son propre cookie de session `GUITARVAULT_DEMO_SESSION`. L’instance habituelle peut rester ouverte sur 8081 avec ses données dans `data/guitarvault.mv.db`. Le profil de démonstration écoute uniquement sur la machine locale.

| Compte fictif | Rôle |
| --- | --- |
| `superadmin@guitar-vault.test` | `ROLE_SUPER_ADMIN` |
| `admin@guitar-vault.test` | `ROLE_ADMIN` |
| `editor@guitar-vault.test` | `ROLE_EDITOR` |
| `superuser@guitar-vault.test` | `ROLE_SUPER_USER` |
| `user@guitar-vault.test` | `ROLE_USER` |

Mot de passe de démonstration commun : **`DemoGuitar2026!`**. Il est haché avec BCrypt dans la base. Pour choisir un autre mot de passe lors du **premier** chargement :

```sh
FIXTURES_PASSWORD='AutreMotDePasse!' ./mvnw spring-boot:run -Dspring-boot.run.profiles=fixtures
```

Les comptes sont déjà vérifiés ; le chargement n’envoie aucun email et ne nécessite pas Mailpit. Pour tester les parcours d’inscription et de récupération sur cette instance, démarrer Mailpit comme indiqué plus bas ; les liens pointent vers 8082.

`AppFixtures.java` prépare également cinq articles (trois publiés et deux brouillons) et sept instruments répartis entre les comptes. Le chargement entier est transactionnel. Le marqueur `guitar-vault-demo-v1` dans `fixture_loads` empêche de rejouer un chargement déjà terminé : les textes, mots de passe, rôles et suppressions modifiés pendant les essais sont conservés au redémarrage. Changer `FIXTURES_PASSWORD` après le premier chargement ne réinitialise donc pas les comptes. Aucune purge automatique n’est effectuée. Une collision avec un compte déjà présent lors du premier chargement annule l’opération, sans modifier ce compte.

Les fixtures ne s’activent qu’avec le profil `fixtures`. Le chargeur refuse les profils `prod`/`production` et toute base persistante autre que `data/guitarvault-demo` ; les tests utilisent une base H2 en mémoire indépendante. Le démarrage normal n’exécute pas les fixtures.

## Rôles

Les cinq rôles sont cumulables et enregistrés dans `user_roles`. Tous les comptes conservent `ROLE_USER`, y compris les comptes créés avant cette table. L’inscription publique attribue uniquement `ROLE_USER` et exige toujours la vérification de l’email. Les champs de rôle envoyés par le navigateur sont ignorés.

`ROLE_ADMIN` et `ROLE_SUPER_ADMIN` peuvent gérer tous les articles, les publier, les remettre en brouillon et les supprimer. `ROLE_EDITOR` peut créer, modifier et prévisualiser uniquement ses propres brouillons ; la publication passe par un administrateur. Il ne peut pas modifier un article déjà publié ni lire les brouillons d’un autre auteur. `ROLE_SUPER_USER` conserve actuellement les permissions d’un membre, en attendant la définition des fonctions avancées. Les rôles administratifs n’ouvrent pas les collections privées des autres membres.

L’attribution d’`ADMIN` par `APP_ADMIN_EMAILS` reste compatible avec les comptes existants. Elle s’ajoute aux rôles enregistrés pour les comptes vérifiés. Aucun écran d’attribution des rôles n’est ajouté par les fixtures ; les rôles de démonstration sont définis dans le chargeur. Aucun rôle `SUPER_ADMIN` n’est attribué au compte personnel : seul le compte fictif de la base de démonstration le reçoit.

## Journal et administration des articles

L’accueil affiche les trois derniers articles publiés sous le bloc de bienvenue et son lien d’inscription. `/articles` propose le journal public avec recherche par titre/chapeau, filtre par rubrique et pagination. Chaque article dispose de sa page de lecture, de son auteur, de sa date et d’une estimation du temps de lecture. Le démarrage normal n’ajoute aucun article de démonstration.

L’espace `/admin/articles` permet de créer, modifier, prévisualiser, publier, remettre en brouillon et supprimer les articles selon les permissions du compte. Il affiche les compteurs, une recherche, les filtres de statut/rubrique et une liste paginée. La suppression demande une confirmation sur une page dédiée. Les brouillons, leurs couvertures et leurs aperçus restent privés : les administrateurs y accèdent tous, les éditeurs uniquement à leurs propres brouillons. Les articles et couvertures sont persistés en base.

Pour attribuer le premier accès administrateur, configurer **l’adresse exacte d’un compte que vous contrôlez**, puis démarrer l’application :

```sh
APP_ADMIN_EMAILS='votre-adresse@example.com' ./mvnw spring-boot:run
```

Créer ce compte via `/signup` s’il n’existe pas, vérifier son email avec Mailpit, puis se connecter. Le lien « Administration » apparaît dans la navigation. Plusieurs adresses peuvent être séparées par des virgules ; la casse et les espaces autour des adresses sont ignorés. Aucun accès administrateur n’est attribué par défaut, ni depuis le formulaire d’inscription. Les administrateurs utilisent les mêmes comptes, mots de passe et vérifications que les autres membres. Redémarrer l’application puis se reconnecter après modification de cette liste (ne pas utiliser de sessions persistantes lors d’un changement de droits).

En local, vous pouvez aussi placer `app.admin-emails=${APP_ADMIN_EMAILS:votre-adresse@example.com}` dans `config/application.properties` depuis le dossier `guitar-vault`. Ce fichier est exclu de Git et chargé automatiquement au démarrage. Cette écriture permet à `APP_ADMIN_EMAILS` de remplacer l’adresse locale.

Un article contient un titre (160 caractères), une rubrique, un chapeau (500 caractères), un contenu en texte simple (50 000 caractères, retours à la ligne conservés) et une couverture JPEG/PNG facultative (5 Mo, 25 mégapixels, 10 000 pixels par côté maximum) avec sa description accessible obligatoire. Le chapeau et le contenu sont obligatoires à la publication ; un brouillon peut être incomplet. Aucun HTML saisi n’est exécuté. Une couverture peut être remplacée ou retirée ; les images sont séparées des données des listes pour éviter de les charger inutilement.

« Enregistrer en brouillon » retire un article déjà publié du site public. L’aperçu montre la dernière version enregistrée. En cas de modification concurrente, publication ou suppression à partir d’une ancienne version, l’opération est refusée pour préserver le travail récent. Les erreurs de validation conservent les textes ; un fichier doit être sélectionné à nouveau. Si la requête entière dépasse la limite d’import, rouvrir le formulaire : la version enregistrée reste inchangée.

Les libellés du journal et de l’administration sont disponibles en français et en anglais. Le contenu d’un article est affiché dans la langue de rédaction.

Un accès refusé affiche une page de récupération : elle distingue un compte sans droits administrateur d’un formulaire dont le jeton de sécurité a expiré, notamment après un redémarrage. Elle permet de changer de compte ou de rouvrir le formulaire. La requête refusée n’est pas exécutée et les protections restent actives. Après un redémarrage, recharger les formulaires déjà ouverts avant de les envoyer.

```sh
./mvnw spring-boot:run
```

Ouvrir <http://localhost:8081/signup> pour créer un compte. Le lien est également disponible dans la navigation et sur l’accueil.

L’inscription enregistre le profil dans la table `users`, normalise l’email et hache le mot de passe avec BCrypt. Les erreurs de validation conservent les informations du profil, sans conserver les mots de passe. Une inscription réussie envoie un email de vérification et redirige vers <http://localhost:8081/login> avec une confirmation. Le compte reste inactif jusqu’au clic sur le lien, valable 24 heures et utilisable une seule fois. Seule l’empreinte SHA-256 du jeton est stockée. Si l’envoi échoue, l’inscription est annulée pour permettre de réessayer.

Pour tester les emails en local :

```sh
docker compose up -d mailpit
./mvnw spring-boot:run
```

Créer un compte sur <http://localhost:8081/signup>, ouvrir l’email dans Mailpit à <http://localhost:18025>, puis suivre le lien de vérification et se connecter. Mailpit capture les emails localement ; il ne les envoie pas à la boîte réelle du destinataire. Le port SMTP exposé est `11025`.

`APP_BASE_URL` permet de configurer l’adresse de l’application dans les liens (par défaut `http://localhost:8081`) et `MAIL_FROM` l’expéditeur. Pour un déploiement réel, configurer également un serveur SMTP de livraison via les propriétés Spring Mail.

La connexion utilise l’email et le mot de passe du compte et ouvre le dashboard. Spring Security gère la session et protège les formulaires contre les requêtes CSRF. Le bouton « Se déconnecter » ferme la session. Le dashboard et les pages internes nécessitent une connexion.

Le tableau de bord à <http://localhost:8081/dashboard> affiche uniquement la collection du compte connecté : nombre total d’instruments, statuts (actif, à réparer, en vente) et cinq derniers ajouts. La collection complète se trouve dans « Mes instruments ». Le bouton « Ajouter un instrument » permet d’enregistrer un nom/modèle, une marque, une année facultative et un statut. Le propriétaire est fixé par le serveur à partir de la session connectée.

La configuration locale utilise une base H2 **persistante** dans `data/guitarvault.mv.db` : les comptes et instruments sont conservés après un redémarrage. Ce dossier est exclu de Git. Les tests Maven utilisent une base en mémoire distincte. Le pilote PostgreSQL est également disponible pour un déploiement.

Les comptes créés avec l’ancienne base en mémoire ont été perdus lors du dernier arrêt et doivent être recréés puis vérifiés. Sans compte actif, une demande de réinitialisation affiche la même confirmation mais n’envoie aucun email. En local, les nouveaux emails se consultent dans Mailpit à <http://localhost:18025>.

```sh
./mvnw test
```

Test facultatif de livraison réelle vers le Mailpit local (laisse des emails de test dans l’inbox, le compte temporaire est annulé à la fin) :

```sh
./mvnw -Dmailpit.integration=true test
```

La navigation propose un menu « Français / English » avec une préférence conservée dans un cookie pendant un an. Les pages, messages de validation et emails sont traduits. Le changement de langue conserve la page et ses paramètres, y compris les liens de récupération.

Les champs de mot de passe disposent d’un bouton œil accessible au clavier. « Mot de passe oublié ? » sur la page de connexion ouvre <http://localhost:8081/forgot-password>. Pour un compte vérifié, le lien envoyé par email permet de choisir un nouveau mot de passe pendant 30 minutes, une seule fois. Le nouveau mot de passe doit comporter au moins 8 caractères, dont un caractère spécial. Les anciennes sessions sont expirées après réinitialisation. La réponse à une demande reste identique pour les adresses inconnues ou inactives ; les demandes répétées pour un compte sont espacées d’au moins une minute.

Le renvoi de l’email de vérification est disponible depuis la connexion ou directement sur <http://localhost:8081/resend-verification>. Le serveur génère un nouveau lien d’activation pour les comptes en attente, invalide le précédent et limite l’envoi à une fois par minute. Une erreur SMTP conserve l’ancien lien. La réponse reste identique pour une adresse inconnue ou un compte déjà vérifié. L’email est envoyé dans la langue choisie. Le formulaire de récupération du mot de passe conserve également l’adresse saisie et propose de renvoyer le lien après la première demande.

Le formulaire d’ajout d’instrument propose aussi un numéro de série facultatif (100 caractères, zéros initiaux conservés) et un ancien propriétaire facultatif (200 caractères), affichés dans la fiche. Il accepte jusqu’à cinq photos JPEG ou PNG (5 Mo par photo, 25 mégapixels maximum), une histoire (10 000 caractères) et d’autres informations (5 000 caractères). Les listes de morceaux enregistrés et de concerts proposent des boutons « + » et de suppression, jusqu’à 50 entrées de 500 caractères chacune. Les entrées sont textuelles (titre, artiste, album ou salle, ville, date) et leur ordre est conservé. Les photos sont enregistrées dans la base avec l’instrument. En cas d’erreur de validation, les textes sont conservés et les photos doivent être sélectionnées à nouveau.

Cliquer sur le nom d’un instrument dans le tableau de bord ou la collection ouvre sa fiche avec les photos, l’histoire, les informations et les listes. La fiche et les photos sont réservées au propriétaire connecté.

Le formulaire est organisé en quatre sections avec des raccourcis de navigation : l’essentiel, les photos, l’histoire et la vie en musique. Un résumé suit la saisie du modèle et de la marque, les textes longs ont des compteurs, et l’action d’enregistrement reste accessible en bas de l’écran. Les photos peuvent être ajoutées en plusieurs sélections ou par glisser-déposer, puis retirées individuellement avant l’envoi. Le formulaire s’adapte aux petits écrans et signale les erreurs d’import sans supprimer les photos déjà sélectionnées.

Chaque utilisateur connecté dispose d’une liste de souhaits privée sur `/wishlist`, accessible depuis la navigation et le tableau de bord. Il peut ajouter, modifier et retirer des souhaits (modèle et marque obligatoires, année et notes facultatives). Le retrait passe par une page de confirmation. Les souhaits sont enregistrés séparément des instruments possédés et ne modifient pas les compteurs de la collection. Les textes de l’interface sont disponibles en français et en anglais.

Les profils de groupe sont disponibles sur `/bands` pour les utilisateurs connectés. Le créateur renseigne un nom, puis éventuellement un style, une ville, une présentation et des liens Spotify, Deezer et site web. Les liens doivent utiliser HTTPS ; les liens Spotify et Deezer sont vérifiés par domaine. Ils sont affichés comme liens externes, sans intégration de lecteur ni appel à leurs API.

Un groupe réunit de 1 à 50 comptes actifs. Les nouveaux musiciens sont invités par pseudo exact (un par ligne ou séparés par des virgules), puis acceptent ou refusent leur invitation. Le créateur reste automatiquement membre et est seul autorisé à modifier la fiche et les associations. Modifier la présentation du groupe ne retire pas les membres existants ; les changements de composition passent par des actions explicites. Un musicien peut appartenir à plusieurs groupes. La page `/musicians/{id}` présente son pseudo et ses groupes, sans exposer son email. Les données sont stockées dans `bands` et la table de liaison `band_members`, séparément des instruments et des listes de souhaits.

Les studios disposent d’un annuaire et de fiches sur `/studios`, accessibles aux utilisateurs connectés depuis la navigation et le tableau de bord. Tout compte actif peut ajouter plusieurs studios, sans rôle professionnel spécifique. Seul le créateur peut modifier ses fiches. Le nom est obligatoire ; la ville, le pays, la présentation, les prestations, le matériel, un site HTTPS et un email de contact sont facultatifs. Les textes longs sont limités à 5 000 caractères chacun. L’email du compte n’est jamais repris automatiquement comme contact.

La fiche du studio renvoie vers le profil de son créateur, qui présente également ses studios. Les enregistrements sont conservés dans la table `studios`, avec une relation vers le compte créateur. La gestion d’une équipe de studio et la réservation ne font pas partie de cette version.

L’annuaire `/studios` propose une recherche combinée par ville, pays et fourchette de prix. Les recherches de lieu sont partielles et insensibles à la casse ; `%`, `_` et `!` sont traités comme des caractères littéraux. Il s’agit d’une recherche textuelle par lieu, sans géolocalisation ni rayon kilométrique. Les filtres sont transmis dans l’URL et peuvent être effacés. La rubrique « Mes studios » conserve la liste des fiches gérées par le compte, indépendamment de la recherche.

Le créateur peut renseigner un tarif horaire facultatif en euros, stocké en décimal exact (`hourly_rate`, deux décimales), entre 0 et 999 999,99 €/h. La saisie serveur accepte le point ou la virgule. Les bornes de recherche sont inclusives ; un minimum supérieur au maximum affiche une erreur. Les fiches existantes sans prix restent valides et affichent « Tarif sur devis ». Elles sont exclues uniquement lorsqu’une borne de prix est renseignée. Les critères sont appliqués dans la requête en base.

Le menu « Mon profil » (`/profile`) ouvre la page du compte connecté, et `/profile/edit` permet de la modifier. Les profils existants sur `/musicians/{id}` conservent les groupes et studios associés et présentent désormais un nom affiché facultatif (le pseudo par défaut), la bio, les instruments joués (texte libre, 255 caractères), le niveau, la ville, le pays, les activités et les liens Spotify, Deezer et site web. Les informations déjà renseignées à l’inscription sont reprises. Les activités « Musicien » et « Ingénieur du son » peuvent se cumuler ; elles ne changent pas les rôles ni les autorisations du compte. Le tableau de bord utilise le nom affiché lorsqu’il est renseigné.

Les champs du profil sont facultatifs. La bio reste limitée à 1 000 caractères, le nom affiché, la ville et le pays à 100, et les liens HTTPS à 2 000 caractères (domaines Spotify et Deezer vérifiés). L’email, le nom complet du compte, le mot de passe et les rôles ne figurent pas dans les données du profil consultable et ne peuvent pas être modifiés via ce formulaire. Le pseudo reste stable. Les pages et photos sont accessibles uniquement aux utilisateurs connectés, et les comptes désactivés ne sont pas consultables.

La photo peut être ajoutée, remplacée ou supprimée depuis le formulaire. Elle est stockée dans `profile_photos`, séparément des comptes, et servie avec `Cache-Control: private, no-store` et `X-Content-Type-Options: nosniff`. Le contenu réel doit être une image JPEG ou PNG valide de 5 Mo maximum, 4 096 pixels maximum par côté et 12 mégapixels maximum. Une erreur de validation ne modifie ni les textes ni la photo enregistrés ; les textes saisis sont conservés dans le formulaire, et le fichier doit être sélectionné à nouveau. Les activités sont conservées dans `user_activities` et les liens et nom affiché dans les nouvelles colonnes nullable de `users`.

Les demandes de devis studio sont accessibles depuis « Demander un devis » sur une fiche studio et depuis « Mes demandes » (`/quotes`) dans le menu et le tableau de bord. Le demandeur renseigne un titre (150 caractères maximum), une description (5 000 caractères maximum), des dates souhaitées facultatives et un budget total facultatif en euros. Les dates doivent être à partir du jour courant en UTC ; une fin nécessite un début et ne peut pas le précéder. Le budget total est indépendant du tarif horaire du studio. Les montants acceptent le point ou la virgule, jusqu’à deux décimales, entre 0 et 999 999,99 €.

La demande est liée au studio désigné par l’URL et au compte connecté ; les identifiants fournis dans le formulaire ne peuvent pas changer ces participants. Un utilisateur ne peut pas adresser de demande à son propre studio, ni à un studio dont le responsable est désactivé. La liste sépare les demandes envoyées et celles reçues pour tous les studios gérés par le compte. Seuls le demandeur et le responsable du studio peuvent consulter les détails. Les emails de compte ne sont pas affichés aux autres participants.

Le demandeur et le responsable peuvent poursuivre une discussion privée avec des messages de 5 000 caractères maximum, présentés dans l’ordre d’envoi avec auteur et date en UTC. Seul le responsable peut joindre un montant total proposé facultatif à un message ; chaque proposition est conservée dans l’historique. Un message du musicien remet la demande en `PENDING` (en attente du studio), une réponse du studio la passe en `ANSWERED`. Les compteurs du tableau de bord suivent ce statut, sans suivi des messages non lus. Un verrou en base sérialise les envois pour une même demande. Les nouveaux messages sont stockés dans `studio_quote_messages` ; les anciennes réponses de `studio_quotes` restent visibles et sont archivées une seule fois lors du premier nouvel envoi. Les consultations ne modifient pas les données. Les messages enregistrés ne sont ni modifiables ni supprimables depuis l’application. Ce parcours reste un échange dans l’application, sans email automatique, réservation, paiement ni acceptation contractuelle du devis.

Les fiches studio peuvent désormais préciser leur capacité d’accueil (1 à 1 000 personnes), les tarifs de mixage et de mastering par titre, un forfait journée et des précisions tarifaires (1 000 caractères). Ces champs sont facultatifs et les montants sont stockés en décimal exact, comme le tarif horaire existant. La recherche par prix continue à comparer uniquement les tarifs horaires ; elle ne mélange pas les prix au titre et à la journée. Les capacités apparaissent aussi dans les cartes de l’annuaire.

Le créateur peut ajouter jusqu’à cinq photos par studio et retirer individuellement les photos existantes depuis le formulaire. Les ajouts et retraits sont appliqués uniquement à l’enregistrement, après validation de tous les champs et fichiers. Les photos doivent être des JPEG ou PNG valides, de 5 Mo maximum chacune, 10 000 pixels maximum par côté et 25 mégapixels maximum. Elles sont conservées dans `studio_photos`. Les galeries chargent uniquement les identifiants ; les données d’une image sont chargées séparément par `/studios/{id}/photos/{photoId}`, réservé aux comptes connectés, avec cache privé désactivé et `nosniff`. Les identifiants des photos à retirer doivent appartenir au studio modifié. Un verrou sur le studio protège la limite de cinq photos lors de modifications concurrentes.

La navigation distingue « Mon espace » (tableau de bord, profil, instruments, souhaits, groupes, studios et demandes) et « Découvrir » (articles, annuaire des studios, groupes). Les menus utilisent des éléments HTML `details` et restent utilisables sans JavaScript. Le JavaScript permet de fermer le menu au clic extérieur, à la sélection d’un lien ou avec Échap. Un lien d’évitement mène au contenu principal ; la page courante est signalée dans les menus et les liens d’administration restent conditionnés aux autorisations existantes.

Le tableau de bord personnalisé affiche le profil, les totaux des groupes rejoints, studios gérés, souhaits et demandes de devis envoyées, ainsi que des aperçus de trois éléments avec liens vers les listes complètes. Les « projets studio » correspondent aux demandes de devis existantes, sans nouvelle entité de projet. Les demandes reçues en attente sont mises en avant pour les responsables de studio ; les réponses disponibles sont comptées côté demandeur (ce compteur ne désigne pas des messages non lus). Les requêtes sont limitées au compte connecté et les aperçus à trois enregistrements en base. Les cinq derniers instruments et les compteurs de collection restent disponibles. Les liens « Mes groupes » et « Mes studios » ouvrent leurs sections du tableau de bord ; « Tout voir » rejoint la liste complète correspondante.


Les invitations de groupe sont disponibles sur `/invitations`, depuis « Mon espace », le tableau de bord et la fiche du groupe. Les invitations reçues et celles envoyées pour les groupes créés par le compte sont privées. Un destinataire ne devient membre qu’après acceptation ; un refus ou une annulation par le créateur n’ajoute aucun membre. Les associations déjà présentes dans `band_members` sont conservées sans demander de nouvelle acceptation.

Le champ des pseudos dans la création et la modification du groupe envoie des invitations, sans remplacer la liste des membres. Une invitation déjà en attente n’est pas dupliquée ; un membre actuel n’est pas réinvité. Un créateur peut relancer explicitement une invitation refusée ou annulée, ou réinviter une personne ayant quitté le groupe. La limite de 50 places comprend les membres et les invitations en attente. Un refus ou une annulation libère une place. Tous les pseudos sont validés avant d’enregistrer la fiche et les invitations.

Les membres peuvent quitter le groupe et le créateur peut retirer un membre après une page de confirmation. Le créateur reste membre et responsable : il ne peut pas se retirer ni être retiré. Une nouvelle invitation acceptée est nécessaire pour revenir après un départ ou un retrait. Seul le destinataire peut accepter ou refuser, seul le créateur peut inviter, annuler ou retirer. Les actions exigent une session active et une protection CSRF. Les invitations sont stockées dans `band_invitations`, avec une ligne unique par groupe et destinataire et les états `PENDING`, `ACCEPTED`, `DECLINED`, `CANCELLED`. Les mutations verrouillent le groupe en base pour sérialiser les changements de membres et de places. Les notifications restent dans l’application, sans email automatique.

Les groupes peuvent renseigner jusqu’à huit genres libres (100 caractères chacun), séparés par des virgules dans le formulaire, ainsi qu’une région facultative (100 caractères), en complément de la ville. Les genres sont affichés en pastilles sur les fiches et les cartes, y compris sur les profils des musiciens. Les doublons de casse et les espaces superflus sont regroupés. La nouvelle collection `band_genres` conserve les genres ; la colonne historique `bands.genre` reste compatible et les anciens styles sont affichés et recherchables sans migration manuelle. La région est stockée dans une nouvelle colonne nullable. La modification et l’effacement de ces champs restent réservés au créateur et ne modifient pas les membres.

L’annuaire `/bands` propose des filtres combinables `genre`, `region` et `city` : genre exact, région et ville partielles, sans distinction de casse. Les critères sont appliqués en base et les doublons de groupes supprimés. Les caractères `%`, `_` et `!` sont traités littéralement. Les genres du filtre incluent les styles historiques ; les suggestions de régions reprennent les valeurs déjà enregistrées. Les champs restent libres pour convenir aux groupes de différents pays. Les filtres restent dans l’URL, ne réduisent pas « Mes groupes » et disposent d’un état sans résultat et d’un lien de réinitialisation.

Les responsables peuvent créer des liens entre groupes depuis la fiche du groupe destinataire : « Groupes amis » ou « On a joué ensemble ». Pour un concert partagé, une date passée ou du jour (UTC) et un lieu de 200 caractères maximum sont facultatifs. Les deux types de liens peuvent coexister ; chaque type représente une relation unique par paire de groupes. Les demandes restent privées aux responsables concernés et nécessitent une acceptation du destinataire. Les liens acceptés sont affichés symétriquement sur les deux fiches, avec les éventuels détails de concert. Les simples membres ne peuvent pas engager leur groupe.

« Mon espace → Liens entre groupes » (`/band-connections`) regroupe les demandes reçues, envoyées et les liens acceptés pour les groupes gérés. Le destinataire peut accepter ou refuser, l’expéditeur peut annuler, et chacun des deux responsables peut retirer un lien accepté après un écran de confirmation. Un refus, une annulation ou un retrait permet une nouvelle demande avec un nouveau consentement. Les groupes ne peuvent pas se lier à eux-mêmes, ni envoyer de demande vers un responsable désactivé. La table `band_connections` utilise une paire ordonnée d’identifiants et une contrainte d’unicité incluant le type ; les écritures verrouillent les deux groupes dans cet ordre pour empêcher les doublons de demandes croisées. Aucun email n’est envoyé automatiquement.

Les concerts s’ajoutent depuis la fiche d’un groupe, uniquement par son responsable. Un titre (150 caractères), une date valide et un lieu (200 caractères) sont obligatoires ; la ville (100), la description (5 000) et l’affiche sont facultatives. Une date passée peut être renseignée pour compléter l’historique. Les fiches séparent les concerts à venir (aujourd’hui compris, en UTC), passés et annulés. Le responsable du groupe organisateur peut modifier un concert ou l’annuler après confirmation. Un concert annulé reste visible et ne reçoit plus de modifications ni de nouvelles participations.

Après publication, le responsable invite les autres groupes depuis la fiche du concert. Leurs responsables acceptent ou refusent depuis « Mon espace → Invitations aux concerts » ou depuis le concert. Seuls l’organisateur et les groupes ayant accepté sont affichés parmi les participants et sur leurs fiches respectives. Les invitations en attente ne sont pas publiques. Le responsable organisateur ou celui du groupe invité peut retirer une participation ou une invitation après confirmation ; une nouvelle invitation reste possible. La table `concert_participations` garantit l’unicité par concert et groupe, et les mutations verrouillent le concert. Les demandes ne modifient pas les liens d’amitié ni les relations « On a joué ensemble ».

Les affiches sont conservées séparément dans `concert_posters`, et les données textuelles dans `concerts`. La validation de l’image contrôle le contenu réel JPEG/PNG, sa taille (5 Mo), ses dimensions (4 096 pixels par côté) et sa surface (12 mégapixels) avant toute mutation. Les fichiers ne sont pas chargés lors de la consultation des listes. Le service d’images exige une session et utilise `Cache-Control: private, no-store` et `X-Content-Type-Options: nosniff`. Le formulaire permet de remplacer ou retirer une affiche ; un nouvel envoi a priorité sur la case de retrait.

Chaque groupe dispose d’un agenda privé (`/bands/{id}/calendar`) accessible au responsable et aux membres actuels du groupe, depuis sa fiche. Une invitation au groupe non acceptée, un lien d’amitié ou une participation à un concert ne donnent pas accès à cet agenda. Toutes les routes de lecture et de gestion contrôlent cette appartenance côté serveur et retournent 404 aux autres comptes ; les réponses de l’agenda utilisent `Cache-Control: private, no-store`. Seul le responsable peut créer, modifier ou supprimer un événement. Les données privées ne sont jamais ajoutées aux fiches et listes publiques des groupes.

L’agenda propose une grille mensuelle du lundi au dimanche et une liste pour le mois choisi, avec navigation et couleurs par catégorie : concerts, répétitions, studio, promotion, sorties musicales et autres événements. Les concerts de l’organisateur et ceux dont la participation est confirmée sont lus directement depuis les concerts existants, dans la période affichée ; leurs changements, annulations et retraits de participation sont donc répercutés sans duplication. La gestion des concerts reste sur leurs pages. Les autres dates sont conservées dans `band_calendar_events` avec titre (150 caractères), catégorie, date, horaires facultatifs, lieu (200 caractères) et notes privées (5 000 caractères). Une heure de fin nécessite un début et doit être plus tard le même jour. Les horaires sont des heures locales saisies, sans conversion de fuseau ; le mois courant est choisi en UTC, comme les autres classements de dates de l’application. Les sessions studio sont saisies manuellement lorsque leurs dates sont confirmées.

Les événements peuvent être uniques ou hebdomadaires, avec une date de fin obligatoire et inclusive. Les occurrences sont calculées pour la seule période consultée, y compris si la série commence avant le mois choisi ; elles ne sont pas matérialisées en base. Modifier une série modifie toutes ses occurrences ; la suppression, après confirmation explicite, supprime toute la série. Cette première version ne prévoit pas d’exception par occurrence. Les recherches de données sont limitées au groupe autorisé et à la plage de dates affichée.

La cloche des notifications est visible pour les comptes connectés et indique le nombre de notifications non lues (badge limité visuellement à `99+`, compteur exact sur la page). Elle ouvre `/notifications`, une liste privée paginée de 20 éléments, du plus récent au plus ancien, avec filtre des non lues. Ouvrir une notification la marque comme lue puis redirige vers l’élément concerné ; une action permet aussi de la marquer comme lue sans ouvrir, ou de tout marquer comme lu. Ces mutations utilisent POST avec CSRF et sont strictement limitées au destinataire. Consulter la liste ou le compteur ne change pas l’état de lecture. Les réponses sont `private, no-store`. Les liens sont construits côté serveur, limités à des destinations internes connues, et les pages de destination conservent leurs propres contrôles d’accès.

Les nouvelles invitations à rejoindre un groupe, demandes de lien entre groupes, invitations aux concerts, demandes de devis et messages de devis créent une notification dans la table `notifications`, dans la même transaction que l’action d’origine. Les doublons déjà en attente et les actions refusées ne créent rien ; une nouvelle invitation après un refus peut notifier à nouveau. Une action du compte sur ses propres groupes ne produit pas d’auto-notification et les comptes désactivés ne sont pas notifiés. Les notifications contiennent le nom du groupe, du concert ou du projet, sans le texte privé des messages. Le chargement d’une ancienne réponse de devis dans l’historique ne crée pas de fausse notification. Les demandes et messages antérieurs à cette fonctionnalité ne sont pas importés automatiquement.

Le compteur est rendu côté serveur à chaque page et vérifié toutes les 30 secondes sur les onglets visibles via `/notifications/unread-count`, ainsi qu’au retour sur l’onglet. Ce point d’accès exige une connexion et ne renvoie que le compteur du compte courant. La cloche reste utilisable sans JavaScript. Les états de lecture des notifications sont distincts des statuts des demandes et invitations : marquer comme lu n’accepte pas une invitation et ne traite pas un devis. Aucun email ni notification push externe n’est envoyé.

Les comptes connectés peuvent signaler un profil, un groupe, un studio, un concert ou un article publié depuis sa fiche. Le motif est obligatoire ; « Autre » exige une explication (2 000 caractères maximum). Le propriétaire ne peut pas signaler son propre contenu et un même compte ne peut pas ouvrir deux signalements simultanés sur le même élément. Signaler ne masque pas automatiquement le contenu. « Mon espace → Mes signalements » (`/reports`) permet de suivre uniquement ses propres signalements et leur décision, sans accès aux notes internes. Le propriétaire du contenu n’a pas accès à l’identité de la personne qui le signale ni à son dossier.

`ROLE_ADMIN` et `ROLE_SUPER_ADMIN` disposent de la file `/admin/moderation`, filtrable par statut et paginée. Ils peuvent prendre en charge, classer sans suite, masquer ou rétablir un contenu. Chaque action exige une justification interne et conserve son auteur et sa date dans `moderation_audit`. `content_reports` conserve le texte du contenu au moment du signalement, même après modification ou suppression de celui-ci. Les images proposées dans le dossier sont les images actuelles ; leur consultation passe par une route réservée aux administrateurs. Ces pages et ces médias utilisent `Cache-Control: private, no-store`. `ROLE_EDITOR` conserve uniquement ses droits éditoriaux et ne donne pas accès à la modération.

Le masquage est réversible et distinct de la publication d’un article : une modification ordinaire ne le retire pas. Il bloque la fiche et ses médias publics et retire l’élément des recherches et listes concernées, y compris les concerts dans les agendas. Il porte sur l’élément choisi, sans masquer en cascade toutes les autres créations de son propriétaire ; les outils privés de gestion et les historiques restent disponibles. Ce mécanisme n’efface pas le nom d’un musicien des listes de membres existantes.

Seul `ROLE_SUPER_ADMIN` peut suspendre ou réactiver le propriétaire d’un contenu signalé, avec une justification auditée. Il ne peut suspendre ni son propre compte ni un autre super administrateur. La suspension bloque la connexion, expire les sessions enregistrées après validation de la transaction et rejette les autres sessions dès leur prochaine requête. Son état est séparé de la validation d’email : réactiver un compte ne valide pas son adresse. Les nouvelles colonnes `moderation_hidden` et `suspended` ont une valeur SQL par défaut `false` pour conserver le comportement des données existantes.

Les responsables de groupes amis peuvent « Proposer une date » depuis la fiche du groupe ami ou la liste d’amis de leur propre groupe. Le formulaire propose uniquement les groupes gérés par le compte dont l’amitié avec le destinataire est acceptée. Les deux groupes doivent avoir des responsables différents, actifs, et ne pas être masqués. Une date du jour ou future (UTC) est obligatoire ; le lieu (200 caractères) et le message (2 000 caractères) sont facultatifs. Une seule discussion en attente est autorisée par paire de groupes et date, même si les deux groupes la proposent simultanément. Plusieurs projets à des dates différentes restent possibles.

« Mon espace → Propositions de dates » (`/date-proposals`) affiche les discussions privées, paginées par 20. Seuls les deux responsables concernés peuvent lire la proposition et son historique ; les simples membres, autres groupes et administrateurs ne disposent d’aucun accès supplémentaire. Les réponses utilisent `Cache-Control: private, no-store`. Le responsable destinataire de la proposition actuelle peut accepter, refuser ou proposer une autre date ou un autre lieu. Une contre-proposition attend une réponse de l’autre groupe ; toutes les versions sont conservées dans `band_date_revisions`, avec auteur et date d’envoi. Le responsable à l’origine de la discussion peut l’annuler tant qu’elle est en attente.

Chaque création, contre-proposition et décision envoie une notification au responsable de l’autre groupe, dans la même transaction, sans inclure le message privé dans la cloche et sans email. Toutes les mutations exigent une protection CSRF. Les propositions sont conservées dans `band_date_proposals` et verrouillées après les groupes, dans l’ordre des identifiants ; la version affichée dans le formulaire protège contre une réponse à une date devenue obsolète. Les doubles réponses et les discussions closes ne peuvent pas être modifiées. Une amitié retirée, un groupe masqué ou un responsable désactivé empêchent de nouvelles propositions et acceptations ; le refus et l’annulation restent possibles pour fermer une discussion existante.

Accepter confirme l’accord sur la date et le lieu envisagés. Cette première version ne réserve pas de créneau dans l’agenda privé et ne publie aucun concert automatiquement. Le concert peut ensuite être créé depuis la fiche du groupe organisateur, puis le groupe ami invité via le parcours existant.

Le type des notifications est stocké comme texte (`varchar(40)`) avec un convertisseur d’énumération Java. Sur une base H2 existante, la mise à jour du schéma convertit l’ancienne colonne `enum` en conservant les types déjà enregistrés. Cela permet les nouveaux types `DATE_PROPOSAL` et `DATE_PROPOSAL_RESPONSE`, ainsi que l’ajout ultérieur de types, sans rester limité à l’ancienne liste de valeurs H2. Un test de migration vérifie ce parcours depuis l’ancien schéma.

## Luthiers et historique professionnel

`/luthiers` propose un annuaire public et `/luthiers/{id}` une fiche d’atelier publique. Depuis « Mon atelier de lutherie » (`/workshop`), un membre crée sa fiche avec nom d’atelier, localisation, spécialités, présentation et contact professionnel. La fiche reste privée tant que son auteur ne coche pas la publication. L’email du compte n’est jamais publié automatiquement. Les ateliers dont le compte est désactivé, suspendu ou masqué par la modération ne sont plus proposés dans l’annuaire et ne peuvent plus recevoir de demandes.

Depuis la fiche privée d’un instrument, le propriétaire peut demander une inspection, une réparation, un réglage, une modification ou un examen d’authenticité auprès d’un atelier publié. L’écran explique avant l’envoi le partage du nom, de la marque, de l’année, du numéro de série et du texte de la demande. Le luthier ne reçoit aucun accès aux autres instruments, aux photos, aux notes privées ni au reste de l’historique. `/interventions` regroupe les demandes envoyées et reçues. Le propriétaire et le luthier peuvent annuler/refuser une demande tant qu’aucun rapport n’est enregistré ; la demande reste conservée.

Seul le compte du luthier choisi peut enregistrer un rapport. Il indique la date réelle de l’intervention ou de l’examen, les constatations/travaux, les éléments observés et les limites. Pour un examen d’authenticité, la conclusion distingue les éléments cohérents avec l’identité annoncée, les éléments incohérents et l’impossibilité de conclure. Il n’existe pas de certification globale automatique. Les rapports sont attribués au compte connecté, datés et enregistrés avec le nom de l’atelier, le nom de compte de l’auteur et son état de vérification à cette date. Il s’agit d’une attribution applicative, pas d’une signature cryptographique.

Une correction exige un motif et crée une nouvelle version sans remplacer l’ancienne. Les versions précédentes restent lisibles et sont explicitement signalées comme telles. Les formulaires obsolètes sont refusés (HTTP 409) ; un verrou sur la demande sérialise l’ajout de versions et l’annulation. La fiche de l’instrument présente les interventions liées dans son historique professionnel, indépendamment du champ historique libre existant. Les demandes restent privées entre le propriétaire demandeur et le luthier assigné, y compris vis-à-vis des administrateurs. Lors d’un transfert accepté, les rapports suivent le passeport via une vue distincte qui exclut les informations privées de la demande.

La vérification de l’identité professionnelle est une opération administrative distincte (`/admin/luthiers`). Un administrateur doit enregistrer les contrôles effectués ; il ne peut pas vérifier son propre atelier. Les décisions sont conservées dans un journal privé. Modifier le nom, la localisation ou le contact d’un atelier retire sa vérification actuelle et nécessite un nouveau contrôle. Cela ne modifie jamais la mention de vérification figée dans les rapports déjà enregistrés. La vérification concerne l’identité de l’atelier et ne garantit pas ses conclusions sur un instrument.

Les données sont stockées dans quatre nouvelles tables : `luthier_profiles`, `luthier_verifications`, `luthier_interventions`, `luthier_assessments`, sans modification des instruments existants. Le schéma est ajouté par la configuration Hibernate `ddl-auto=update` existante ; les tests utilisent H2 en mémoire. Les preuves peuvent être saisies sous forme de texte et complétées par des pièces jointes dont la visibilité est choisie séparément (voir la section Documents). Les portfolios publics de travaux et la publication sélective des rapports restent des évolutions ultérieures : aucun rapport ne devient public avec la fiche de l’atelier.

Vérification ciblée : `./mvnw -o -Dtest=LuthierTests test`.

## Transferts de propriété entre membres

Depuis un instrument, « Transférer mon instrument » permet d’envoyer une proposition au **pseudonyme exact** d’un autre membre actif. Le propriétaire confirme les informations qui seront partagées. Aucun annuaire de comptes ni recherche par email n’est ajouté. `/transfers` regroupe les propositions envoyées et reçues ; les notifications intégrées annoncent une proposition et sa résolution. Le destinataire ne voit que les identifiants de l’instrument (nom, marque, année, numéro de série) et les pseudonymes des deux parties avant acceptation.

Seul le destinataire peut accepter ou refuser, et seul l’expéditeur peut annuler. Une seule proposition peut être en attente par instrument. Accepter conserve le même instrument, son identifiant, sa date d’enregistrement et son numéro de série. La collection passe au destinataire ; le statut « En vente » revient à « Actif », tandis que « À réparer » est conservé. Les enregistrements et concerts restent attachés au passeport. Les deux comptes doivent être actifs à l’acceptation. Les interventions de lutherie en attente doivent d’abord être terminées ou annulées, afin de ne pas transférer implicitement une commande privée.

Les périodes de propriété sont conservées dans `instrument_ownerships`. La période initiale est créée à la première proposition et commence à la date d’enregistrement de l’instrument dans l’application ; elle ne prétend pas reconstituer sa propriété antérieure. L’acceptation ferme cette période et ouvre celle du destinataire à la même date. L’ancien propriétaire peut consulter l’historique des périodes et ses archives, mais ne peut plus ouvrir la collection privée ni les rapports futurs du nouveau propriétaire. L’historique des périodes n’affiche jamais les pseudonymes des autres propriétaires. Les informations de contrepartie restent accessibles aux deux participants de leur propre proposition.

Les champs libres existants `notes`, `history` et `previousOwner` sont copiés dans les archives privées de la période terminée puis vidés sur la fiche active. Les photos restent en base et attachées à l’instrument, mais sont réservées à leur propriétaire d’origine via `instrument_photos.private_owner_id`. Les photos existantes sans auteur sont attribuées au propriétaire sortant avant le premier transfert. Les autres membres, y compris les administrateurs et le destinataire, ne peuvent pas consulter ces archives ni télécharger ces photos. Les archives du propriétaire sortant restent disponibles depuis « Historique de propriété ». Une facture ajoutée comme photo bénéficie de cette protection. Le module Documents permet aussi de conserver des factures privées et de choisir explicitement certains fichiers à transmettre.

Les rapports professionnels suivent l’instrument, toutes versions et corrections comprises. Le nouveau propriétaire y accède depuis « Rapports professionnels du passeport », une vue qui exclut le texte privé des demandes et l’identité des demandeurs. La version actuelle est distinguée des versions précédentes pour chaque intervention. Les anciens demandeurs et les luthiers conservent l’accès à leurs demandes d’origine ; le nouveau propriétaire n’obtient pas cet accès. Une information financière ou personnelle inscrite directement dans le **rapport professionnel** accompagne ce rapport : les formulaires de demande, de rapport et de transfert explicitent cette règle. Ces informations doivent être conservées dans les notes ou photos privées si elles ne doivent pas suivre le passeport.

Les mutations prennent un verrou sur l’instrument ; les résolutions verrouillent ensuite la proposition et relisent son état. La fermeture de période, l’ouverture de la suivante, la préservation des données privées, le changement de propriétaire et la notification sont atomiques. Les doubles soumissions et actions obsolètes sont refusées avec HTTP 409. La création d’une intervention de lutherie utilise également le verrou de l’instrument, pour empêcher une demande de l’ancien propriétaire de s’insérer après son transfert.

Le schéma existant ajoute deux tables (`instrument_transfers`, `instrument_ownerships`) et la colonne nullable `instrument_photos.private_owner_id` via Hibernate `ddl-auto=update`. Les invitations de personnes sans compte, prix de vente et contrats dédiés restent hors de cette première version. Les pièces jointes sont gérées par le module Documents, avec une sélection par proposition de transfert.

Tests ciblés : `./mvnw -o -Dtest=InstrumentTransferTests,InstrumentTransferConcurrencyTests,LuthierTests test`.

## Documents privés et justificatifs des rapports

Depuis un instrument, « Documents de l’instrument » permet d’ajouter un PDF, JPEG ou PNG de 5 Mo maximum, avec un titre et une catégorie (facture, reçu, certificat, estimation ou autre). Le fichier est privé au contributeur par défaut, y compris vis-à-vis des administrateurs. La page « Mes documents » conserve l’accès aux fichiers ajoutés ou reçus lors d’un transfert accepté, même après revente, et aux pièces de rapports que le lecteur est autorisé à consulter. Les photos privées existantes conservent leurs règles propres : elles ne deviennent pas des documents partagés automatiquement.

Le formulaire de transfert propose les documents de cet instrument que le propriétaire a ajoutés ou reçus explicitement. Aucun n’est coché par défaut. La sélection est figée dans la proposition ; un fichier ajouté ensuite n’y entre pas. Avant acceptation, le destinataire voit uniquement le nombre de fichiers sélectionnés. Après acceptation, il reçoit des droits de téléchargement sur ces fichiers, sans obtenir les autres factures ou fichiers privés. Annuler ou refuser ne crée aucun droit. Les droits déjà accordés sont conservés après revente ; chaque nouveau transfert exige une nouvelle sélection. Le contributeur d’origine conserve son accès. Un document d’un autre instrument ou une pièce de rapport ne peut pas être injecté dans cette sélection.

Sur chaque version de rapport, seul son auteur peut « Joindre un justificatif ». Une nouvelle pièce conserve sa propre date d’ajout et reste liée à cette version ; elle ne remplace pas le rapport ni ses pièces précédentes. Trois choix explicites sont proposés :

- **Moi uniquement** (par défaut) : le contributeur seul peut télécharger le fichier.
- **Moi et le demandeur d’origine** : accès privé aux deux parties de la demande, sans partage avec les propriétaires suivants.
- **Lecteurs du rapport, y compris les futurs propriétaires** : accès au contributeur, au demandeur d’origine et au propriétaire actuel de l’instrument. Cette pièce suit le passeport, indépendamment des fichiers sélectionnés dans un transfert.

Une facture privée ne devient donc jamais visible parce qu’un rapport est partagé. Les listes de pièces sont filtrées selon les mêmes droits que les téléchargements : leurs titres et noms ne sont pas exposés aux autres lecteurs. Les fichiers rattachés à un rapport ou référencés dans une proposition de transfert sont conservés, même si la proposition est ensuite refusée ou annulée. Des justificatifs corrigés peuvent être ajoutés à une nouvelle version du rapport.

« Gérer » permet à chaque lecteur de modifier le titre et la catégorie dans sa bibliothèque personnelle. Les libellés d’origine, les fichiers et les titres affichés dans les rapports et propositions restent inchangés, de même que la bibliothèque des autres lecteurs. L’archivage est personnel et réversible : le fichier disparaît des listes actives et des nouvelles sélections de transfert de ce lecteur, mais les accès existants et les sélections déjà enregistrées restent valides. Le filtre « Documents archivés » permet de le retrouver et de le restaurer.

Seul le contributeur peut supprimer définitivement un téléchargement sans rapport, référence de transfert ni droit accordé. Une page de confirmation précède la suppression du fichier et de ses métadonnées. Le serveur revérifie ces conditions sous le même verrou d’instrument que les transferts : une sélection concurrente et une suppression ne peuvent pas réussir ensemble. La suppression libère une place dans le quota ; l’archivage ne le fait pas. Les formulaires de gestion détectent les versions périmées pour éviter d’écraser une modification plus récente.

« Mes documents » combine une recherche sur le titre personnel, le titre d’origine et le nom de fichier, avec des filtres par instrument, catégorie personnelle, accès et état actif/archivé/tous. Les résultats sont paginés par 20 ; les instruments proposés proviennent uniquement des fichiers accessibles au lecteur. L’accès « Référencé dans un transfert » décrit une référence conservée, y compris pour une proposition annulée ou refusée, sans créer de nouveau droit. La table additionnelle `document_library_entries` conserve les libellés et l’état propres à chaque lecteur.

Les octets sont stockés séparément des métadonnées, dans `document_contents`, pour ne pas charger les fichiers dans les listes. `instrument_documents` conserve les métadonnées, `transfer_documents` la sélection par proposition, et `document_grants` les accès issus des acceptations. L’ajout des droits et le transfert de propriété partagent la même transaction et le verrou de l’instrument. La limite est de 20 fichiers par contributeur et instrument, pièces de rapports comprises ; une proposition peut sélectionner jusqu’à 50 documents déjà disponibles.

Les extensions sont comparées au type détecté ; les images reprennent les limites existantes (5 Mo, 25 mégapixels, 10 000 pixels par côté) et sont décodées pour validation. Les PDF font l’objet de contrôles de base sur leur en-tête et leur marqueur de fin, sans analyse complète de leur structure, signature numérique ou antivirus. Tous les fichiers sont servis uniquement après autorisation, en téléchargement (`Content-Disposition: attachment`), sans cache partagé, avec `nosniff` et une politique CSP restrictive. Aucune prévisualisation intégrée ni publication publique n’est ajoutée. Les octets téléchargés restent identiques au fichier validé.

Tests : `./mvnw -o -Dtest=DocumentTests,DocumentLibraryTests,DocumentLibraryConcurrencyTests,InstrumentTransferTests,LuthierTests test`. Le parcours Chromium dans `tests/e2e/test_passport_journey.py` couvre aussi une facture non sélectionnée, un certificat transmis, un justificatif de luthier partagé explicitement et sa facture privée, ainsi que les libellés personnels, les filtres, l’archivage, la restauration et la suppression confirmée d’un fichier inutilisé.

## Rendez-vous privés avec un luthier

Depuis une fiche publique d’atelier, « Demander un rendez-vous » permet à un membre connecté de contacter le luthier sans avoir préalablement enregistré d’instrument. Le musicien renseigne un objet, un message privé et un créneau futur avec son fuseau horaire explicite (par exemple `Europe/Paris`). Une demande reste en attente jusqu’à l’accord de l’autre participant. Les heures inexistantes ou ambiguës lors d’un changement d’heure sont refusées plutôt que déplacées silencieusement.

« Mes rendez-vous » (`/appointments`) rassemble les demandes envoyées et reçues par l’atelier du compte, par pages de 20. Les deux participants peuvent discuter et proposer un autre créneau tant que la demande attend un accord ; seul l’autre participant peut confirmer ou refuser le dernier créneau. Les propositions et décisions restent dans l’historique. Après confirmation, les messages restent possibles ; chacun peut annuler. Une demande refusée ou annulée est fermée mais consultable. Pour convenir d’un autre créneau après confirmation, créer une nouvelle demande et annuler l’ancienne si nécessaire.

Les notifications sont intégrées à l’application ; aucun email de rendez-vous n’est envoyé. Il n’y a pas de synchronisation avec des agendas externes, de paiement ni de rappel automatique. La confirmation enregistre l’accord des deux participants dans l’application. Le nom de l’atelier et sa localisation sont visibles depuis sa fiche, et les modalités pratiques se conviennent dans la conversation.

Les conversations ne sont lisibles que par le musicien et le responsable de l’atelier, y compris si sa fiche est ensuite dépubliée. Les administrateurs et les futurs propriétaires d’un instrument n’y ont pas accès. Les pages privées utilisent `Cache-Control: private, no-store`. Les mutations exigent le jeton CSRF et une version de formulaire courante, avec verrou en base pour empêcher une confirmation concurrente d’une autre proposition. Les comptes inactifs ne peuvent pas poursuivre la conversation.

Le schéma ajoute `luthier_appointments` et `appointment_messages` via la configuration Hibernate existante. Le type `LUTHIER_APPOINTMENT` utilise le convertisseur varchar des notifications ; le test de mise à niveau couvre aussi l’ancien schéma H2 à enum. Tests ciblés : `./mvnw -o -Dtest=AppointmentTests,AppointmentConcurrencyTests,NotificationSchemaUpgradeTests test`. Le parcours Chromium vérifie aussi la demande, une contre-proposition, la confirmation, les messages privés et l’interface mobile en français.

## Calendrier de disponibilités des ateliers

Depuis « Mon atelier de lutherie », le responsable configure `/workshop/availability` : activation facultative, fuseau, jours travaillés, horaires communs à ces jours et durée de 15, 30, 45, 60, 90 ou 120 minutes. Les dates bloquées couvrent des journées entières, jusqu’à un an à l’avance ; il faut d’abord annuler les rendez-vous confirmés de la journée. L’interface du responsable affiche les visites confirmées et les créneaux libres pour une date choisie.

Si le calendrier est activé, demandes et contre-propositions choisissent un créneau dans les 90 prochains jours, affiché dans le fuseau de l’atelier. Une demande en attente ne bloque rien ; seule la confirmation réserve le temps. Les créneaux de durée complète sont alignés sur l’ouverture et exclus s’ils chevauchent une réservation, une date bloquée ou un changement d’heure ambigu. Les musiciens ne voient jamais les identités ou objets des autres rendez-vous. L’annulation libère immédiatement la réservation. Le sélecteur fonctionne sans JavaScript.

Les mutations de calendrier et de rendez-vous prennent d’abord le même verrou d’atelier, puis celui du rendez-vous éventuel. La disponibilité est relue lors de la confirmation : deux confirmations concurrentes qui se chevauchent ne peuvent pas réussir ensemble, pas plus qu’une confirmation et le blocage de sa journée. Les formulaires de créneaux incluent la version de disponibilité ; une modification des réglages impose de recharger les choix.

Le schéma ajoute `workshop_availability`, `workshop_working_days` et `workshop_blocked_dates`. Les rendez-vous et messages de proposition conservent leur durée dans une colonne nullable : les anciennes lignes sans durée utilisent 30 minutes. Les visites confirmées gardent leurs instants et leur durée lors d’un changement de réglages. Un calendrier non activé conserve les propositions libres de 30 minutes, avec contrôle de chevauchement à la confirmation. Il n’y a pas d’horaires distincts par jour, de pause partielle ni de répétition de rendez-vous dans cette version.

Tests ciblés : `./mvnw -o -Dtest=AvailabilityTests,AvailabilityConcurrencyTests,AppointmentTests,AppointmentConcurrencyTests test`. Le parcours Chromium couvre aussi les réglages, une journée bloquée, le sélecteur et les contre-propositions, la réservation, sa confidentialité, l’annulation, le déblocage et la vue mobile.

## Suivi des travaux en atelier

Une intervention existante peut désormais suivre un dépôt physique : réception avec état et accessoires, devis chiffré et révisable avant accord, acceptation ou refus par le propriétaire, début et avancement des travaux, notification de disponibilité puis retrait enregistré par le luthier. Le rendez-vous propose un accès aux instruments du demandeur avec l’atelier présélectionné. La liste des interventions affiche l’étape des travaux. Les montants sont des décimaux exacts (deux décimales au maximum), taxes applicables comprises ; EUR, USD, GBP, CAD et CHF sont proposés. Le paiement reste convenu directement entre les participants.

Le journal daté conserve chaque réception, devis, décision et changement d’étape. Chaque mutation vérifie la version courante et prend le verrou d’instrument avant celui de l’intervention, dans le même ordre que les transferts. Deux réceptions ou une acceptation et une révision concurrentes ne peuvent pas réussir ensemble. L’acceptation porte sur le devis consulté ; les travaux ne commencent qu’après accord, et un devis accepté ne peut plus être révisé. Avant accord, chacun peut annuler ; ensuite, seul le luthier enregistre l’annulation, avec motif et modalités de restitution. Le retrait et l’annulation clôturent définitivement le dossier.

Les devis, décisions et notes restent privés entre le demandeur et l’atelier. Les notifications sont intégrées à l’application, sans email spécifique aux travaux. Les rapports signés existants constituent l’historique transmissible ; leur signature ne clôt pas les travaux. Un dossier actif bloque l’acceptation d’un transfert même après signature du rapport. Les nouvelles tables `workshop_jobs` et `workshop_job_events` sont ajoutées par la configuration Hibernate existante, sans changer les anciens statuts d’intervention.

Tests ciblés : `./mvnw -o -Dtest=WorkshopJobTests,WorkshopJobConcurrencyTests,LuthierTests,InstrumentTransferTests,NotificationSchemaUpgradeTests test`. Le parcours Chromium inclut la réception, le refus et la révision d’un devis, son acceptation, l’avancement, la notification, le retrait, la confidentialité après revente et la vue mobile française.


### Accord sur les travaux supplémentaires

Pendant les travaux, le luthier peut proposer une modification avec motif de découverte, ensemble des travaux révisés, nouveau total dans la devise existante et date de fin estimée. La proposition suspend les travaux sans changer l’accord en vigueur. Seul le propriétaire peut accepter la version courante ; son accord applique les nouvelles conditions et reprend les travaux. Un refus laisse les travaux suspendus. Le luthier peut réviser la proposition, l’annuler en reprenant explicitement les seuls travaux déjà acceptés avec une explication, ou annuler le dossier. Les actions d’avancement, disponibilité et retrait sont bloquées pendant cette suspension.

Les événements de proposition et de décision conservent les montants, travaux et dates concernés ; les anciens accords restent lisibles. Chaque mise à jour conserve les mêmes verrous et contrôles de version. La date de fin estimée doit être actuelle à l’acceptation. Les nouveaux champs des dossiers et événements sont nullables pour les anciennes lignes ; le statut utilise désormais un convertisseur varchar, avec test de mise à niveau depuis l’ancien enum H2. Tests : `WorkshopJobTests`, `WorkshopJobConcurrencyTests`, `WorkshopJobSchemaUpgradeTests` ; Chromium couvre également le refus, la reprise du périmètre initial, la révision, l’accord et l’écran mobile français.

## Boutiques vintage, inventaire et visites privées

`/shops` est l’annuaire public paginé des boutiques, avec recherche par nom ou localisation. Chaque fiche `/shops/{id}` affiche les coordonnées et horaires fournis par le responsable et son catalogue paginé, filtrable par nom ou marque. `/my-shop` permet à tout membre de créer et publier sa boutique, de gérer ses annonces et de consulter ses échanges. Une fiche publiée ne vaut pas vérification professionnelle ou certification des instruments.

Une annonce `/shop-listings/{id}` référence un passeport existant appartenant au responsable, ou crée un nouvel instrument dans sa collection. Le nom, la marque et l’année sont copiés pour l’annonce ; seuls la description de vente, le prix demandé, la devise, l’état disponible/réservé/vendu et une photo publique distincte sont ajoutés. Les notes, numéros de série, photos privées, documents et rapports ne sont pas publiés. Les prix utilisent des décimaux exacts à deux décimales ; EUR, USD, GBP, CAD et CHF sont proposés. Boutique et annonce doivent être publiées. Les instruments vendus quittent le catalogue, et un transfert accepté masque automatiquement l’ancienne annonce et sa photo publiques. Marquer vendu ne transfère pas le passeport et ne déclenche aucun paiement.

Les photos JPEG/PNG de 5 Mo maximum utilisent les contrôles de décodage existants et sont stockées séparément des listes. Les brouillons et leurs photos sont privés au responsable. Chaque modification d’annonce invalide les anciens formulaires, y compris un remplacement de photo. Les publications prennent le verrou de l’instrument, comme les transferts : une annonce ne peut pas être publiée par un ancien propriétaire, et deux annonces actives pour le même instrument ne peuvent pas être publiées ensemble.

`/shop-conversations` réunit les contacts et rendez-vous privés. Une demande peut concerner une annonce (nom et prix demandé figés), ou la boutique sans instrument. Les participants peuvent discuter et proposer un créneau explicite ; seul l’autre peut confirmer ou refuser la dernière proposition. Les visites durent 30 minutes. Le verrou de boutique sérialise les confirmations et empêche les chevauchements ; l’annulation libère le créneau. Les horaires de la fiche sont informatifs et les visites nécessitent un accord explicite. Il n’y a pas de calendrier automatique d’ouverture pour les boutiques. Les conversations restent privées après dépublication ou vente, sans accès administratif ni publication dans le passeport. Les notifications sont intégrées à l’application. Les règles de fuseau et de changement d’heure sont partagées avec les rendez-vous de luthier.

Le schéma ajoute `vintage_shops`, `shop_listings`, `shop_listing_photos`, `shop_conversations` et `shop_messages` via la configuration Hibernate existante. Les tests `ShopTests` et `ShopConcurrencyTests` couvrent publication, confidentialité, prix et stock, photos, transferts, échanges et confirmations concurrentes ; `NotificationSchemaUpgradeTests` couvre le nouveau type de notification. Le parcours Chromium couvre une boutique, une annonce liée au passeport, un instrument nouvellement créé avec prix, une visite privée, le stock réservé/vendu, le mobile français et le masquage après transfert.

## Interface : Tailwind CSS et daisyUI

Le socle Thymeleaf utilise Tailwind CSS 4 et daisyUI 5, avec un thème local et des icônes SVG. Aucun CDN, police distante ou serveur Node n’est nécessaire pour exécuter l’application. Le CSS compilé `src/main/resources/static/css/app.css` est versionné : les commandes Maven habituelles restent suffisantes.

Pour modifier l’interface, installer les dépendances avec `npm ci`, puis lancer `npm run watch:css` pendant les modifications, ou `npm run build:css` avant de livrer. Les sources sont dans `src/main/frontend/app.css`, les composants partagés dans `templates/ui.html` et la structure dans `templates/layout.html`. Inclure le CSS généré dans les changements. Tailwind utilise le préfixe `ui:` et daisyUI `dui-` (exemple : `ui:dui-btn`) ; les anciennes pages restent compatibles via une couche CSS dédiée.

La navigation personnelle devient une barre latérale sur ordinateur et un menu repliable sur mobile. Le tableau de bord affiche des aperçus privés de la collection, les approbations à traiter et les rendez-vous confirmés à venir. Le passeport organise ses rubriques en onglets accessibles au clavier ; sans JavaScript, toutes les rubriques restent lisibles. Les aperçus respectent les participants des demandes et les propriétaires privés des photos, y compris après transfert.
